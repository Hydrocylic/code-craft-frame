## 背景与动机

- **实践触发**（virtual-human 项目，2026-08-21）：同一问题（VRM 资产处理与制作流程）被切成 `vrm-asset-management` 与 `vrm-production-workflow` 两个任务——本质是同一问题的细节与进度递进，靠"任务来源与继承"衔接
- **用户观察到的个人倾向**：为减轻 Agent 对话上下文负担而冲动切割任务 → 任务碎片化风险
- **框架现状缺口**：有"分叉"（新任务继承状态快照）与"封存"（总结封存），但缺**聚拢**环节——合并 / 改名 / 吸收的正式动作与记录方式

---

## 核心原则（提案）

**任务生命周期脱离 Agent 对话上下文而存在**：

- 任务的**制定、变更、执行、封存**全部以文档形式落盘（plan / log / code-review / 改名记录）
- 任何新对话或新 Agent 只靠文档即可接手——Agent 是执行者，不是任务状态的载体
- 推论：既然 plan/log 是文档，**任务文件名允许改名**；前提是存在改名记录（旧名→新名、内容去向、引用关系），历史可追溯

---

## 提案环节：任务收拢（Task Consolidation，暂定名）

### 触发时机（候选）

1. **任务封存时**——将现有"总结封存"动作扩展为"联合收拢 + 封存"
2. **信息积累至需梳理方向时**——与现有执行日志的"状态总结"条目挂钩
3. **定期回顾时**

### 动作序列

1. Agent 重读相关 plan + log（多任务横向，而非单任务纵向）
2. 以收拢为目标识别碎片：同一问题的多任务、进度递进的任务对、可被吸收的子任务
3. 出方案：合并 / 改名 / 吸收 / 封存，附改名记录与引用关系表
4. 征求确认 → 执行

### 防碎片化判据

- **开新任务的条件**：独立交付物，或独立阶段边界清晰
- **"记录"本身不构成新任务理由**——记录已有归宿：知识 → knowledge-base.md，决策 → decisions.md，宏观 → overview/，时间线 → 执行日志 + 状态总结条目
- **冲动切割前的检查**：能否并入现有任务？能否靠"状态总结"条目承载？

## 实践记录（第一轮：virtual-human，2026-08-26）

### 本轮决策

- **归宿**：保持扁平 + 🔒 锁机制。不建 archive 子目录、不敲定"终结形式"——似完未完的情况较多，敲定终结形式消耗成本；若扁平目录超载，复盘时再议
- **线头机制（新增概念）**：封存 ≠ 终结。每个封存任务保留"线头"——未竟事项清单，以时间戳 + 文件路径（或 issues IS-XXX）指向；封存任务有解封环节，除非明确放弃某些进一步开发/技术选型，均留待复盘或遇新问题时重新启用
- **收拢自身的落盘**：保守扁平——新开 `tasks/task-consolidation-plan.md` + `task-consolidation-log.md`（收拢也是任务，但占位与普通任务相同，不给独立子目录/更高层级）

### 第一轮实践动作

- `minimal-pipeline` + `lipsync-prototype`：状态行 🔒 + 文末封存条目（线头清单）
- `vrm-asset-management` + `vrm-production-workflow`：联合封存待 W1 打通（触发条件：R03 烘焙轮 + 标准流程首跑验证通过）
