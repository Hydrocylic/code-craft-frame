# 框架局限性

> 区域: explore（探讨区）
> 框架版本: v2.0
> 最后更新: 2026-08-07

---

## 已知局限

### 1. 框架较重，不适合快速原型

**问题**: 完整的课程轮次→实验→简历流程对快速验证想法的场景过于繁重。

**缓解**: 框架设计哲学中已声明"不适用于快速原型验证"。如果只是快速试一个想法，直接在 `experiments/` 下创建代码跑一下即可，不需要完整的轮次笔记。

**未来可能**: 增加"轻量模式"——仅需一个 `notes.md` 而非完整的三件套（notes + qa + code-refs）。

### 2. 三类型体系的边界在极端情况下模糊

**问题**: 一个"重构到一半发现应该有产品级质量"的项目可能在 reconstruction 和 product 之间摇摆。

**缓解**: 转换规则已定义了 reconstruction → product 的标准流程。建议先完成 reconstruction 的学习目标再考虑转换，而非边学边转。

**未来可能**: 增加"混合模式"标记，允许项目同时具备两种类型的部分特征。

### 3. 对非代码类学习（理论、数学）的支持不足

**问题**: 框架以"代码是学习的第一载体"为核心信念，对纯理论学习（如读论文、推公式）缺乏明确指引。

**缓解**: 可以将论文视为"参考项目"，按 reference 类型处理。`notes/` 中的分析笔记可以承载理论内容。

**未来可能**: 增加"理论参考"子类型，或以独立文档描述理论学习的适配方式。

### 4. 环境管理对多项目共用同一环境的情况支持不足

**问题**: 多个项目可能共用同一个 conda 环境或 CMake 预设，但 `envs/` 的结构是全局的，没有"该环境服务于哪些项目"的映射。

**缓解**: 在 `envs/README.md` 中手动记录环境与项目的对应关系。

### 5. 跨仓库框架同步是手动的

**问题**: 当母库中的 `_framework/` 更新后，消费者仓库需要手动复制同步。

**缓解**: CHANGELOG 机制使同步可追踪，但同步动作本身仍是手动的。对于 git submodule 的使用者，可以将 `_framework/` 本身作为 submodule 引入，但这增加了复杂度。

---

## 不适合使用的场景

1. **团队协作的开发项目** — 框架为单人学习设计，不包含 code review、CI/CD、issue tracking 等团队协作规范
2. **微服务/大型系统** — 框架的项目粒度适合单人可把控的规模
3. **生产环境的运维** — 框架不涉及部署、监控、告警
4. **需要严格合规的项目** — 框架不包含安全审计、合规检查流程
