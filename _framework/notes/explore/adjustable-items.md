# 可调整内容

> 区域: explore（探讨区）
> 框架版本: v2.0
> 最后更新: 2026-08-07

---

## 说明

以下内容是框架中可以**根据具体场景调整**的部分。这些不是"错误"，而是框架设计的柔性边界——在某些场景下偏离标准做法是合理的。

---

## 目录结构层面

### 1. 引用源位置

**标准**: 参考源码放在 `reference/<name>/<source>/`

**可调整**: 如果参考源码过大（如完整克隆的 Linux 内核），可以：
- 在 `reference/<name>/` 中只放分析笔记，源码路径在 README.md 中说明
- 使用 git submodule 减少仓库体积
- 将源码放在仓库外的文件系统中，笔记中用绝对路径引用

### 2. envs/ 目录

**标准**: envs/ 放在仓库根目录

**可调整**: 如果所有项目使用同一环境且不需要版本管理：
- 可以完全省略 `envs/` 目录
- 环境配置可以放在 `notes/resources/` 中作为参考资料

### 3. notes/ 全局笔记

**标准**: notes/ 放在仓库根目录，包含 daily/、concepts/、resources/

**可调整**: 随着项目增多，concepts/ 中的概念笔记可能需要重新组织（如按领域分子目录）。这是在预期之内的，不影响框架规则。

---

## 项目类型层面

### 4. 项目可以跳过类型

并不是所有内容都需要归入三种类型之一：

- 临时探索的代码 → 直接放在 `experiments/` 下，不需要 meta.yaml
- 快速验证想法 → 创建轻量级的 notes 文件即可
- 外部工具的配置文件 → 放在 `envs/` 或项目 README 中说明

### 5. 项目类型的"灰色地带"

某些项目可能同时具备两种类型的特征：

- **分析+重构**: 一个 reference 项目中包含了少量的实现验证代码 → 要不要转为 reconstruction？如果实现量小且只是为了验证理解，保留在 reference 中即可
- **重构+产品**: 一个 reconstruction 项目的产出质量已经接近产品级 → 要不要转为 product？如果学习目标已达成，可以转换；如果还想继续学习，先不动

### 6. 轮次粒度

**标准**: 每个轮次聚焦一个独立的知识点/实现模块

**可调整**: 轮次的粒度取决于：
- 学习者的背景知识（初学者需要更细的粒度）
- 参考项目的复杂度（大型项目需要更多轮次）
- 实验的独立程度（能独立跑的轮次通常更适合）

---

## 模板层面

### 7. 模板不是必须完全填写

模板中的所有节都是建议，可以：
- 删除不适用的节
- 添加自定义的节
- 如果某个轮次不需要 Q&A，qa.md 可以很简短

### 8. meta.yaml 的额外字段

标准字段之外，可以自行添加：
- 个人评分（对自己学习质量的评估）
- 时间追踪（实际花费的小时数）
- 自定义状态（在 planned/in-progress/completed/archived 之外）

---

## 同步层面

### 9. 框架同步频率

**标准**: 每次 CHANGELOG 变更后检查所有项目的 meta.yaml

**可调整**: 当项目数量多时，可以：
- 只检查 active 状态的项目
- 批量更新（积累若干变更后一次性同步）
- 对 archived 项目跳过同步
