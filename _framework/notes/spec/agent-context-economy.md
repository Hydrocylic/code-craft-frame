# Agent 上下文消耗分析与对策

> 区域: spec（规范区）
> 框架版本: v3.0
> 创建: 2026-09-05
> 来源: 实例长对话实践复盘（一个对话横跨多轮、几十次工具调用后的诊断）

## 一、上下文消耗大头（按实测占比排序）

1. **文件变更通知**：用户在 IDE 中编辑笔记文件，系统每次回显变更 diff（几十次 × 数十至上百行）——最隐蔽的大头，且不可由 Agent 控制。
2. **IDE 诊断 hook**：每次代码文件编辑后回传 lint / diagnostics 信息（PostToolUse 附加输出）。
3. **长对话跨多轮**：工具调用结果（文件内容、命令输出、系统提醒）全程保留在历史中，没有压缩点；轮次越多，历史越大。
4. **长问答文件全量进出**：qa.md / notes.md 数百行时，每次读写整体经过上下文。

## 二、对策（按性价比排序）

> **补：切对话的五选项决策树**（由外部 skill 资料吸收）。上面第 1 条只说“**该切了**”，没说“**切哪种**”——五种动作，按场景选：

| 动作 | 什么时候用 | 代价 |
|---|---|---|
| **继续**（Continue） | 还在同一段紧密推理里，上下文没到信号阈值 | 无（但会持续吃上下文） |
| **压缩**（Compact） | 同一任务、只要抹掉过程性内容 | 低；**可能丢细节**，故先确保结论已落盘 |
| **交接**（Handoff） | **跨对话 / 跨工作区 / 交同事 / 主线中途岔出侧任务** | 中：按需写本地执行交接（模板 `templates/session-handoff.md`）；正式结论先落产出，分别检查产出自足与接力安全 |
| **独立执行线** | 侧任务可并行、主线不必共享其推理过程，且用户决定另开对话 | 中：先有唯一任务契约，按需生成 kickoff 与本地交接；启动仍由用户执行 |
| **一鼓作气**（Push） | 只差一小段就收口 | 低；但**别用它逃避落盘**——先落盘再收口 |

**判据一句话**：**动作跟着“服务对象的边界”走**——同一服务对象能用“继续/压缩”，换服务对象才考虑“交接 / 独立执行线”；是否交接取决于未完状态，不以名册历史或归档仪式为理由。交接与产出分开，按总纲与手册的产出/交接标准；不能只靠交接记忆维持产品或规则的完整性。

1. **按任务切对话**（最有效）：每个清楚的任务单元开新对话；正式结论先进入长期产出，未完现场确有需要时才用本地 handoff 接力。判断信号：上下文使用过半、工具调用 > 20 次、或横跨两个服务对象。不要用交接记忆替代当前正文。
2. **对话产出走文件、聊天只给摘要**：完整答案进入对应读物、任务正文或必要证据；聊天回复压到“要点 + 文件指针”。已授权、可逆且范围内的动作直接完成；非阻塞待决集中到检查点；权限、安全、不可逆动作和实质冲突才及时打断。
3. **当前正文优先，历史按问题查询**：冷启动只读入口、唯一任务契约与必要现行正文；归档、原始日志、上游库和 Git 历史只围绕明确问题限定范围查询。若正常任务必须考古才能继续，优先补当前正文。
4. **小范围读写**：Read 用 offset/limit、Grep 定位代替全文件 Read；编辑用短且唯一的 anchor；收到文件变更通知后只针对变更点行事，不重复读全文。
5. **主动提示切换**：Agent 在长对话中应主动建议压缩或开新对话（用户认可该节奏后，提示本身就是任务的一部分）。
6. **用户侧可选项**：IDE 插件的 diagnostics 回传如可静默能再省一块（插件配置，Agent 不可代改）。

## 任务记录的最小正文

适用于任务计划、dispatch、交付、规则反馈和接力；功能定义与必要验收不能为了短而省略。

- **只写会改变下一动作的信息**：结论、未解决问题、必要证据和下一步。普通内部取舍、已解决的探索弯路、遵守了哪些通用规则，不另写报告。
- **默认篇幅**：交付/交接争取一屏（约 20–40 行），单条问题 1–3 行；这是删冗余的目标，不是截断安全事实或契约的硬限额。无需写字数合规证明。
- **交付四项**：结果及对应任务项；实际版本与验证摘要；未通过/未验证及影响；下一动作。文件改动由 diff 查，只有影响行为或复核的符号才点名。
- **测试一行一组**：工作目录/版本共写一次，命令、结果/退出码、必要失败项、原始输出指针放同一行。实现自查、读取他人证据、独立复跑分清；不默认重复全量测试。长哈希表、全量输出和排查轨迹留证据文件，按问题取读。
- **问题只留事实与动作**：现象/最小复现 → 影响 → 下一步；已解决则更新原项，不新增一份分析账。没有后续价值的探索不落盘。任务线执行后有规则发现时，在本任务 dispatch 各维护一份 `<ID>-rule-feedback.md`，无发现不建空件；每项只写问题/建议/框架处置，允许压缩已解决内容，不要求只增不减。
- **用户只审裁定点**：功能取舍、范围变化、验收底线与真实风险；已批准决定的措辞和范围内常规实现由 agent 完成。权限缺口、数据安全、共享写入冲突和失败不能隐去，压成一条可处理问题即可。
- **一处为准**：计划管当前状态，契约管范围/验收，交付管本批证据，人工单管操作；互相引用，不复制。旧指令直接改为当前动作，不叠加修订说明让接手者自行拼接。
- **先写可执行范围**：契约可事先授权有边界的目录/模块及必要测试，不强求预知每个文件；禁止触及的共享接口另列。既有契约明确要求逐文件批准时仍须遵守，不能用“任务必需”自行补记授权或事后追认。

## 三、与既有机制的关系

- **当前正文 + 本地交接**：当前正文承载可持续使用的结论；工作区起点 `_local/<ID>/handoff.md` 只在存在未完现场时接续，不能成为产品或规则正本。
- **文件是真相源**：聊天是通知与短答通道；内容按用途进入规范、阅读材料、任务契约或必要证据，不因“落文件”就全部混进日志。
- 本文件是**规范**（Agent 行为准则）；高频边界按需摘要到根 `AGENTS.md`，不复制完整条款。

## 四、局部修改纪律

改文件里的一小段时，**上下文消耗不该按整个文件计价**。四条：

1. **定位用 grep，不读全文**：`rg -n "<锚点>" <file>` 拿到行号即可；
2. **只读目标区域**：Read 用 offset/limit 覆盖“区域 ± 数行边界”，不把区域外内容拉进上下文；
3. **验证只回读改动区**：不做全文件校验（除非改动跨多个区域）；
4. **报告不回传全文**：只给“文件 · 范围 · 行数变化 · 一句话摘要”。

> 来源：一次 260 行文件只改 25%，却付了“全文 + 一次性脚本 + 二次核对 + 修补”约 600 行上下文。

## 五、工具化值不值

给“要不要为某件事写脚本 / 工具”一个算式：

```text
净收益 = 复用次数 × 单次节省 − 理解成本 − 维护成本 − 误导成本
```

- **收益全在“复用次数”**：新 agent 理解一个工具（读说明 + 接口语义）本身要花上下文，**用不到 2 次就不划算**；
- **优先替换“不可替代的能力”**，而不是“不方便的操作”——若原生能力（如“匹配即范围”的区域编辑）已覆盖，工具只能靠“纪律”取胜，而纪律不必靠脚本；
- **接口要便宜**：一条命令 + 一屏 `--help` 是上限；**说明比代码长**即说明设计过重；
- **写成流程就会把人带沟里**：工具是“需要时取用”，一旦进了必读清单，后续任务会在不合适的场景硬套它（同型教训：`deliveries/`、`sessions/`、`notes/` 三个落点约定在失效后仍被沿用）。

> 反面实例：某次局部编辑工具建后观察 4 周仅实战 1 次，随后降级为**备用**；
> 正面实例：实例中每轮都在用的领域量采集 / 比对脚本，收益项是正数。
