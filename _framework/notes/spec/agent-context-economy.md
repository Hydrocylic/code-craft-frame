# Agent 上下文消耗分析与对策

> 区域: spec（规范区）
> 创建: 2026-09-05
> 来源: webgl-path-tracer r08–r10 长对话实践复盘（一个对话横跨三轮、几十次工具调用后的诊断）

## 一、上下文消耗大头（按实测占比排序）

1. **文件变更通知**：用户在 IDE 中编辑笔记文件，系统每次回显变更 diff（几十次 × 数十至上百行）——最隐蔽的大头，且不可由 Agent 控制。
2. **IDE 诊断 hook**：每次代码文件编辑后回传 lint / diagnostics 信息（PostToolUse 附加输出）。
3. **长对话跨多轮**：工具调用结果（文件内容、命令输出、系统提醒）全程保留在历史中，没有压缩点；轮次越多，历史越大。
4. **长问答文件全量进出**：qa.md / notes.md 数百行时，每次读写整体经过上下文。

## 二、对策（按性价比排序）

1. **按轮次/任务切对话**（最有效）：每轮或每 2–3 个函数解析开新对话；靠交接记忆（memory 文件）接力——"文件是真相源"纪律的天然配套。判断信号：上下文使用过半、工具调用 > 20 次、或横跨两个轮次。
2. **对话产出走文件、聊天只给摘要**：标准解答 / 逐行解析全文入 qa.md，聊天回复压到"要点 + 文件指针"级别。
3. **小范围读写**：Read 用 offset/limit、Grep 定位代替全文件 Read；编辑用短且唯一的 anchor；收到文件变更通知后只针对变更点行事，不重复读全文。
4. **主动提示切换**：Agent 在长对话中应主动建议 `/compact` 或开新对话（用户认可该节奏后，提示本身就是任务的一部分）。
5. **用户侧可选项**：IDE 插件的 diagnostics 回传如可静默能再省一块（插件配置，Agent 不可代改）。

## 三、与既有机制的关系

- **交接记忆**（memory 系统）：切对话的接续点——`webgl-path-tracer-handoff.md` 为项目范例（当前进度 + 待办 + 协作约定）。
- **问答三区 + 文件是真相源**：保证"聊天变短"不丢信息——内容都在文件里，对话只是暂存区。
- 本文件是**规范**（Agent 行为准则）；多次验证后可并入根 CLAUDE.md 行为约束。
