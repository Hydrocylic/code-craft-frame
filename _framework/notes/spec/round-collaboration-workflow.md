# 轮次协作工作流规范

> 区域: spec（规范区）
> 框架版本: v2.2
> 创建: 2026-09-03
> 来源: webgl-path-tracer 项目实践（r00–r08 多轮验证，2026-08-26 ~ 09-03）

## 适用范围

reconstruction 项目的 curriculum 轮次协作（Agent + 用户）。product 项目的 tasks/ 工作流见 task-note-system.md。

## 一、轮次文档形态

1. **方案进轮次目录**：`<slug>-plan.md` / `<slug>-log.md` 配对放轮次目录；项目级提案（proposal）只保留整体定位、跨轮次路标、更改记录，不承载轮次级计划
2. **两件套为默认**：notes.md + qa.md（code-refs.md 可选——实践显示代码路径引用直接写进 notes/qa 更轻，项目可决策不创建）
3. **挂 plan 的条件**：有设计取舍或产出独立代码的轮次挂 plan/log；纯概念/复读轮两件足够
4. **plan 是活文档**：执行中决策变更追加「动态调整记录」节；**内容提前/推迟**（跨轮次调度变更）必须记入 plan 动态调整 + log 双处

## 二、问答流程（notes ↔ qa）

1. **三区管理（问题缓冲 / 待解答 / 已解答）**：
   - **问题缓冲**：暂存不成熟或易钻兔子洞的问题（搁置理由可写可不写——非硬性），防止细节问题拖垮整体进度；每轮收尾过一遍——成熟 → 转入待解答，作废 → 划掉（2026-09-05 起，webgl-path-tracer r09 提出；同日用户修正：理由条目不设硬性要求）
   - **待解答**：用户新增问题入此区；Agent 作答入 qa.md 后移动到「已解答」并标注 `→ 已解答 qa.md Qn`
2. **自检题闭环**：轮次收尾出 3–5 道自检题入 notes；用户作答后 Agent 给「标准解答 + 思路对照」入 qa——对照明确区分"方向对但需精确化"与"方向反了"两类
   - **自检题设计三准则**（2026-09-09 吸收自 libs/research-field-onboarding 的 checkpoint 设计规则，与 r02–r07 自检题实践互证）：
     1. **可指认出处**——必须能指向笔记中写明答案的句子；答错的读者应能回头找到答案
     2. **范围限定**——只考本轮刚教的概念，不能要求轮次未陈述的知识（错答应揭示讲解漏洞，不是读者背景缺口）
     3. **前提匹配**——一个恰好只掌握所标记前置的读者应能作答
   - **错答处理**：换一种解释，而不是更大声地重复同一种解释
3. **用户实验优先**：用户对现象的观察/实验结论 > Agent 的预设理论。Agent 解释被用户实验推翻时，**认错并保留勘误记录**（原错误叙述 + 更正标注，不静默改写历史）
4. **参考代码可勘误**：参考仓库的代码/注释/大纲也会错；"权威不可靠，推导才可靠"——发现勘误记入 notes 差异记录 + qa（先例：GW specular 填空大纲符号颠倒）
5. **多轮问答**：细节密集的轮次允许多轮问答后再进入下一轮（用户节奏优先）
6. **代码注释 = 疑问的非正式作答**：代码阅读中产生的疑问可就地写成代码注释；Agent 解答分两档——**简答走注释**（注释内一两句的非正式作答）、**完整推导或跨轮次引用才入 qa.md**；注释里悬而未决的疑问在轮次收尾时转入 notes 遗留问题三区，不留悬空问号（2026-09-07 起，webgl-path-tracer r10-review 品读提出——第 1 次验证）

## 三、代码轮执行流程

1. **方案先行**：决策点表（建议 + 理由）在对话中确认后才落盘代码
2. **验证归用户**：npm/dev/build 指令写入 plan 标注"待用户执行"；验证反馈（含问题现象）由用户贴回、Agent 记入 log
3. **验证场景设计责任**：场景/参数要能让目标现象**可读**（例：光源太小导致目标效果淹没在噪声里——改场景，不改架构）
4. **现象分层**：先区分"预期统计现象"（如无 NEE 的噪声、O(1/√N) 收敛）与"真实 bug"；前者写进 notes 作为现场课，后者按 shader 错误四层（编译/链接/校验/运行）排查
5. **快速推进方针**：学习期代码克制（最小可行）；参考项目的自建系统只留标记、挂知识路标，不为细节停步
6. **GitHub 访问/拉取前置计划**：涉及 GitHub 访问与拉取的操作（fetch / clone / pull / submodule add|update|sync 等联网获取类）必须先写入 plan——写明**目的、需求、放置位置、用途**，由用户执行；Agent 不临时发起拉取类指令（2026-09-08 起，webgl-path-tracer r15 合并收尾用户确认；子模块拉取与样例模型下载均按此流程实践）
7. **收尾提交只给 comment**：Agent 提供收尾提交时**只写 commit message，不写完整 bash 指令**（heredoc 过长且用户只需 message）。格式定稿（2026-09-08，webgl-path-tracer r16 T6 用户选定）：

   ```
   <轮次> <线头标签>: <行为摘要> — <补充·为什么/影响/线头关联，可省略>
   ```

   - 轮次 + 线头标签（如 `r16 T1:`）= **索引字段**，放最前——git log 扫描/排序友好
   - 行为摘要 = 改动本身（英文祈使式，与仓库历史一致）；补充段 = 为什么/影响，与摘要**不重复**（只重复一种说法就省略）
   - 例：`r16 T1: make auto scene config scale-invariant — boombox/avocado were dark and clipped`
   - 分支卫生类（分支删除等）无 commit；品读型分支的历史提交不追溯改写
8. **图片读取边界**：图片文件**只读属性信息**（尺寸/格式/文件大小等元数据），**不读内容、不尝试读内容**——包括像素采样、base64 展开、canvas 解码等一律不做；诊断需要图像信息时改走字符图/数值读回/属性元数据（2026-09-08 起，webgl-path-tracer 用户定调，承接"不要读图"原则）
9. **脚本测试最小化**：**代码分析优先，脚本测试尽量少用**——分析结果很费 token；脚本只在"无头可验且必要"时才跑，且测试方法要落地成可复用脚本（check-*.mjs）或记入 log，不写一次性脚本（2026-09-08 起，webgl-path-tracer r16 BUG-009 排查期用户定调）

## 四、收尾状态同步清单（每轮必做）

- [ ] meta.yaml rounds 追加
- [ ] curriculum/README 轮次状态
- [ ] 项目 README 轮次表（completed + 日期）
- [ ] 轮次 plan 状态 → ✅
- [ ] 全局执行日志追加条目
- [ ] 跨轮次影响（编号勘误、内容提前/推迟）→ 提案/curriculum README 同步

## 五、对话交接纪律

1. **文件是真相源**：回答用户问题 = 先写文件再回复总结；对话是暂存区
2. **交接前清空对话**：换新对话前，所有未落盘的答案、待办、决策必须写回文件（notes/qa/log/memory）
3. 每个执行条目带日期；格式沿用 task-note-system
