# 任务协作工作流规范

> 区域: spec（规范区）
> 框架版本: v3.0（2026-10-19 由实例实践回推并取最大公约数）
> 创建: 2026-09-03
> 来源: 多个实例的多轮协作实践（项目标识已去化）

> **求同存异**：本规范只收跨工作区成立的通用工作流。角色词表、任务目录名、轮次编号、验证命令与产品路径由实例决定；只对某个项目成立的细节留在实例，不强行合并。标“可选实践”的条目默认不启用，实例可按需采用。

## 适用范围

通用任务协作（Agent + 用户）。无需先选项目类型或轮次编号才能执行任务；简单任务可以直接在现有正文完成。

## 一、任务文档形态

1. **按内容需要建件**：任务目录没有固定必备文件组；能在已有正文中自足表达的内容不拆新件，空文件和只含占位符的文件不创建。

   | 文件 | 何时有 | 承载什么 |
   |---|---|---|
   | `notes.md` | 有值得长期保留的学习笔记、问题推理或实验观察 | 知识与推理；不承担任务授权或当前状态 |
   | `qa.md` | 确有问答、自检或教学闭环 | 问题、答案与思路对照；没有问答就不建 |
   | `<theme>-plan.md` | 工作跨多个步骤、存在依赖/取舍，或需要独立验收 | 目标、范围、步骤、卡点、任务契约与验证门槛 |
   | `<theme>-log.md` | 执行过程本身有长期价值，或跨多次操作需要按时间追踪 | 决策、异常、验证反馈与计划变更 |
   | `<theme>-manual-tasks.md` | 人工步骤较多、需复制命令或需结构化回收反馈 | 人工操作与反馈单 |
   | `<theme>-plain-plan.md` | 非技术读者需要单独拍板 | 通俗目标、做法与已定决定；声明技术 plan 为正本 |
   | `<theme>-conventions-card.md` / `<theme>-record-sheet.md` | 共享口径或人工采集确有独立复用价值 | 可复用定义或采集结构，不复制 plan 正文 |

   最小形态可以只有一段现有正文；复杂任务再逐步增加 plan、log 或人工单。文件数量不是完成度指标。

2. **按服务对象命名**：在 `<task-dir>/` 中可用 `plan.md`、`design.md`、`survey.md` 等短名；同目录确有多个同类产出时才加主题前缀。保留存量文件名，不强制改名；不要求 notes/qa 或日志成套生成。

3. **plan 与 log 分别按需**：有多步依赖、设计取舍、独立产物或验收边界时建立 plan；只有执行时序、异常或验证过程值得独立保存时才建立 log。短任务直接在 plan 或交付件写完成结果，不要求双写。plan 是活文档：执行中的有效决定直接更新对应正文；需要保留变化理由时再加简短调整记录。

4. **执行地图只写“步骤与卡点”**：长任务可在 plan 列步骤 / 谁 / 前置卡点，不要求逐件登记目录内文件角色与状态。目录读法用一两句说明带过即可。

5. **plan 必含「验证门槛」**：写清“达标才进下一步”的判据，且必须**可判定**——数值容差、结果/位图对拍、不变量断言、明确的通过-失败条件。禁止“看起来正常”“目测没问题”这类无法判定的表述；门槛不达标时的分支（补做 / 降级 / 绕过）也要写。

   - **性能 / 真机类另加「采集协议」**：① 指标定义（分子分母、被什么上限钳制）；② 取样序列（何时取、取几张、如何保证标注值 = 实际值）；③ 裁切 / 排除约定（哪些帧不计入、上采样与重采样如何处理）；④ 成本与负载（总时长、最小必要采集集）。性能数字的第一失真源常常不是门槛而是量定义与取样序列。
   - **基线数字要带「测法」**：plan 里任何基线快照（行数 / 体积 / 用例数）都要给出取数命令，原样粘贴；手抄估算值与实测会漂。预期值也要先复算再写。
   - **结构 / 重构类门槛要可执行、可复算**：优先落成结构测试或独立复算脚本，不各轮自写口径；复跑方应独立复算，不只引用测试绿。
   - **带外部依赖（provider / 网络 / 长会话）的任务**：门槛加一条**可诊断性**——连接/请求状态可见、当前卡在哪一步可见、卡死时可导出会话事件或日志。

6. **验证手段先声明**：本轮用无头单测、浏览器内对拍还是不变量探针，在 plan 里写明；参考实现缺测试时，本项目的验证设施本身是主要交付物之一。交付时造出的可复用用例 / 探针，交付后单独立项搬进代码仓，否则等于没留下。

7. **测试前置自检（preflight）**：性能 / 真机 / 无头类任务在开始测量前先跑环境自检（平台层 / 应用层 / 产物层 / 过程层），不过就中止且不产出数据。细则见 [`test-preflight.md`](test-preflight.md)。

8. **口径卡（可选）**：被 plan / 交付件多处引用的口径（量定义、判据、引用红线）独立成 conventions-card，避免同一口径抄进多处后各自漂移。

9. **任务粒度**：以“能不能独立验证”为准——一个任务 = 一个能独立跑 / 独立达标的单元。背景越生疏、参考越庞大，粒度拆得越细。

10. **开设控制**：新功能 / 后续工作优先并入现有任务，不轻开新任务目录；开设新目录需有明确门槛（用户授权 + 现有任务确实无法承载）。任务完成后的后续任务基于长期设计/代码现状确立，不从上一任务的残留范围派生。

## 二、问答流程（notes ↔ qa）

1. **三区管理（问题缓冲 / 待解答 / 已解答）**：问题缓冲暂存不成熟或易钻兔子洞的问题，防止细节拖垮整体进度；收尾过一遍，成熟转待解答，作废划掉。用户新增问题入待解答；Agent 作答入 qa 后移到已解答并标注 `→ 已解答 qa.md Qn`。

2. **自检题闭环**：任务收尾出 3–5 道自检题入 notes；用户作答后 Agent 给“标准解答 + 思路对照”入 qa，明确区分“方向对但需精确化”与“方向反了”。自检题设计三准则：

   - **可指认出处**：必须能指向笔记中写明答案的句子；
   - **范围限定**：只考本轮刚教的概念，不要求未陈述的知识；
   - **前提匹配**：一个恰好只掌握所标记前置的读者应能作答。

   错答处理：换一种解释，而不是更大声地重复同一种解释。允许判“跳过”，在 qa 写一行记录即可，不阻塞收尾。

3. **用户实验优先**：用户对现象的观察/实验结论 > Agent 的预设理论。Agent 解释被用户实验推翻时，认错并保留勘误记录（原错误叙述 + 更正标注，不静默改写历史）。

4. **参考代码可勘误**：参考仓库的代码/注释也会错；发现勘误记入 notes 差异记录 + qa。

5. **多轮问答**：细节密集的任务允许多轮问答后再进入下一步（用户节奏优先）。

6. **代码注释 = 疑问的非正式作答**：简答可就地写成代码注释（一两句非正式作答）；完整推导或跨任务引用才入 qa。注释里悬而未决的疑问在收尾时转入 notes 遗留问题区，不留悬空问号。

## 三、代码任务执行流程

> 角色词表由实例决定；下面只写职责边界，不绑定具体 job 名。

### 3.1 职责边界

| 职责 | 做什么 | 不做什么 |
|---|---|---|
| **任务组织** | 起草 plan（目标 / 范围 / 任务 / 验证 / 收尾）；维护任务契约与最小 kickoff；查收与组织验收；按需收尾 | 不写代码；不做性能采集；不改规则区与产品定义 |
| **实施** | 按任务表实现；交付前自查（类型 / 构建 / 接口）；交付相关测试与最小验证设施 | 不扩范围；不直写主干；不改规则区与产品定义 |
| **调试** | 查因、复现与修复；同批完成相关回归与最小复现设施 | 不承担新功能实现 |
| **独立验证（按需）** | 按明确验证问题独立取证、复杂复现或大批量结果分析；原始输出留文件 | 不是每批必经；最终判定归用户；不改产品/测试代码 |
| **设计 / 架构（按需）** | 需求与方案、模块边界与重构步骤 | 不写代码；不代替用户拍板 |
| **只读解读（按需）** | 只读既有代码，产出结构化描述 / 地图 / 差异记录 | 不写不改代码；不改需求 |
| **用户** | 派遣（开对话）；人工验收；依赖安装 / 联网 / 构建；git 写操作 | — |

**调度链**：任务组织在 plan 中明确任务契约 → 用户确认范围与决策点 → 任务组织生成简短 kickoff（只指向契约，不复制正文）→ **用户派遣** → 实施 / 调试实现、自查并交付 → 任务组织查收与组织验收（核 diff / 契约 / 证据）→ 有缺陷交回实施修复 → 通过（最终判定归用户）→ 收尾。

**进入方式与角色职责分开**：用户可直接指定执行线，也可使用任务安排方提供的 kickoff。kickoff 按需生成，但不进正式任务正文；两族均读取唯一任务契约，不因角色不同再造派工文件。

### 3.2 三条硬约束

1. **不代发**：即使环境支持直接起子线 / 子代理，派工方也不得代发；执行线一律由用户粘贴 kickoff 启动。
2. **默认不拆线**：一个任务一条线、可跨多轮；并行只在用户明确要求时用。管理成本优先于表面效率。
3. **拍板 ≠ 放行**：拍板后等用户阅读任务契约，再由用户决定是否启动执行线。

### 3.3 验证分工

| 验证的哪一段 | 默认归属 |
|---|---|
| **实现自查**：复现、相关测试/最小设施编写、修复后回归 | 实施 / 调试，与实现同批；独立通用设施建设才考虑另开任务 |
| **交付查收**：读 diff、核范围/契约/证据、识别未通过与人工待验项 | 任务组织；获任务级命令授权后可针对性复核，不代写实现或测试代码 |
| **专项验证**：独立取证、复杂复现、大批量自动化结果分析 | 按需独立验证线，不是每批必经；由用户启动 |
| **人工体验与最终验收** | 用户；agent 提供人工单与记录格式 |

**先定验证问题，再定执行者**。需要专项验证的触发包括：实现自报与现象不一致；数据丢失、撤销历史、导入兼容等高风险面需要反证/故障注入；跨模块/版本的大量场景超出轻量查收；需要证明测试能抓住原缺陷；或用户明确要求独立验证。

**证据层次必须分清**：读实施方输出是“核对交付证据”，不是独立复跑；读 diff 是静态查收，不足以宣称运行通过；实施线以外的执行者在明确版本上实际运行检查，才记录为“独立复跑”。

**实施交付证据口径**：以实现为主，承担与改动直接相关的最小自检与必要回归，不等于免测；先定向验证，最终版本如获授权且成本低，可跑一次全量与类型检查，不对未变版本重复全量。遗留失败、测试设施重构、浏览器专项或跨模块长排障，记录复现、影响与证据后交任务组织定范围，由用户按需启动调试/验证。原始输出落文件，对话只回退出码、用例摘要、首个相关失败与证据路径；不删断言、不压真实失败来缩短交付。

**内容描述与问答**：任务期内归任务组织（写进 notes / qa / log）；任务外另开线（只读解读 / 研讨）；成稿后的文字修缮只做措辞、指针与已记录事实的回填，不产新结论。

### 3.4 实施纪律

1. **约束分级后实施**：任务契约把要求分为三层——**硬约束**（用户可见行为、数据安全、兼容接口、验收底线与授权范围；不得擅改）、**建议路线**（内部拆分、算法、命名与实现顺序；在授权路径和共享接口边界内可调整）、**待证假设**（交互可达性、性能预估、竞态是否存在；先做最小检查，不机械落代码）。已授权、可逆且不改变硬约束的建议路线不逐项等待聊天确认；产品含义变化仍由设计/用户裁定。
2. **事实反馈回路**：发现反例或契约不可实施时，记录最小复现/事实 → 说明对验收与用户行为的影响 → 给最小修订建议 → 只暂停受影响部分；未受影响的已授权工作继续。
3. **验证责任与执行权限分开**：任务单写明命令、工作目录、执行者与用户授权。未授权的测试/构建/服务步骤落人工单，标“待用户执行”；获明确授权后由实施、任务组织或按需独立验证执行，保存原始输出。视觉判定仍归用户，性能验收须独占机器。
4. **验证场景设计责任**：场景/参数要能让目标现象**可读**（例：光源太小导致目标效果淹没在噪声里——改场景，不改架构）。
5. **现象分层**：先区分“预期统计现象”与“真实 bug”；前者写进 notes 作为现场课，后者按错误层次排查。
6. **快速推进方针**：学习期代码克制（最小可行）；参考项目的自建系统只留标记、挂知识路标，不为细节停步。
7. **GitHub 访问/拉取前置计划**：涉及联网获取（fetch / clone / pull / submodule add|update|sync）必须先写入 plan——写明目的、需求、放置位置、用途，由用户执行；Agent 不临时发起拉取类指令。
8. **收尾提交只给 message**：默认只交可复制的消息，不写提交命令。起草前按 [`git-practices.md` §0](git-practices.md#commit-message)；细节与验证证据留日志。
9. **图片读取边界**：图片文件只读属性信息（尺寸/格式/文件大小等元数据），不读内容、不尝试读内容——包括像素采样、base64 展开、canvas 解码等一律不做；诊断需要图像信息时改走字符图/数值读回/属性元数据。
10. **脚本测试最小化**：代码分析优先，脚本测试尽量少用；脚本只在“无头可验且必要”时才跑，且方法要落地成可复用脚本或记入 log，不写一次性脚本。可复用脚本要有索引（一行一个：用途 + 何时用）。
11. **引入参考项目须登记「复现条件」**：写明能否在干净 clone 上跑起来、需要哪些外部资产、资产由谁提供、缺资产时哪些部分仍可分析；缺资产的参考要给出替代路径。参考库只读；上游引用是线索，不是本产品验收判据。结论写成“我们采用 X 做法（因为 Y）”，不要求点名上游行号/符号/commit。真借了代码的那一份必须能说清版本与许可，并保留第三方声明。
12. **数据由人类录入的任务形态**：性能 / 真机类任务的 Agent 产物是采集协议 + 记录表模板 + 口径卡，不是数字；数字由用户在真机上采集并录入。Agent 不接触测试机器、不写估计值。
13. **画面效果类工作的验证回路（可选实践）**：处理明暗、色调、观感时，判据 = 人工参与 + 运行数据采集，不许用模型识图当判据。Agent 提供验证设计/假设/采集方案与数值读回，用户完成判断。
14. **测试流程优先于测试结果**：测试的首要目的是跑通流程（验证设施端到端可用），结果本身不是目的；不为数字完备性加任务，采集规模可按“够验证流程”收缩。
15. **人工步骤按复杂度决定落点**：单个简短步骤可直接写在任务契约或 plan 中；步骤较多、需要复制命令、跨多处操作或需要结构化回收反馈时，才建立人工任务单。起草时先检查输入设备、焦点和前置状态能否让用户自然完成；不可自然触发的程序状态改用获授权的自动化验证或明确辅助触发条件。命令标明 shell、每行一条；用户报告“完成”不自动等于结果已经生效。
16. **范围外发现**：实施/查收中发现不属于当前任务目标的问题，先在任务 plan 的「范围外发现」节记一行（现象 / 影响 / 证据 / 建议去向），不直接改范围。影响当前验收 → 当前任务或调试线；范围外缺陷/技术债 → 新任务或承接清单；产品/设计缺口 → 设计候选；无归属 → 收件箱。紧急/阻塞项停受影响部分并问用户。

## 四、收尾检查（按实际产物选择）

收尾不是同步所有台账。只检查本任务实际涉及的项目：

- **结果与范围**：唯一任务正文已写明完成项、未完成项、范围变化和下一动作；没有第二份状态正本。
- **验证证据**：注明取证版本、实际命令、结果和未验证项；历史绿灯不代替当前证据。
- **当前摘要**：只有根入口或跨任务待办确实引用本任务状态时才同步其短摘要，并指回任务正本。
- **人工步骤**：存在人工任务单时，核对反馈与仓库事实；未执行的步骤明确去向。
- **范围外发现**：已记入任务 plan 并分诊到去向；未确认项不写成已完成。
- **运行状态**：确有并行或接力风险时在当次 kickoff/交接中说明；只有未完执行状态需要跨对话接手时才写工作区起点 `_local/<ID>/handoff.md`。
- **临时件**：本线产生的脚本、截图、探针、构建产物应在工作区起点 `_local/<ID>/`，结束时清理或说明保留条件。
- **Git 消息与格式**：需要提交时按 [`git-practices.md` §0](git-practices.md#commit-message)起草消息；当前文本运行 `git diff --check`。

没有对应产物或风险的项目直接跳过，不为勾清单补建 notes、qa、log、人工单、交接件或全局日志。

## 五、对话接力

1. 已确认结论先更新唯一正式正文；聊天不作为长期正本。
2. 同一任务换对话但没有未提交面、占用资源或未完推理时，只提供任务契约路径和下一动作，不建 handoff。
3. 确有未完执行状态时，写最小本地 handoff（模板 `templates/session-handoff.md`）；不要求把同一内容分别写入 notes、qa、log 或其他 memory 文件。
