## 目的与适用

一个仓库常常同时有**多个 Agent 会话 + 人类**在协作：内容线在写轮次、实施线在改代码、框架线在改规则、
人类在调度与验收。接口没被定义过时会出现三类问题：**分工靠话题**（话题会变）、**交接靠印象**（印象会丢）、
**归档靠感觉**（感觉会错）。

本 spec 定义这套协作的接口：谁是谁（身份）、谁干什么（派工）、谁还活着（生命周期）、怎么交接（三件套）。
**不依赖特定平台或工具**——只用版本库里的文档表达。

## 一、身份：ID 与服务对象

1. **ID = `<job>-<YYMMDD>`**：`job` 表功能（**不表轮次号**），日期用**该对话的创建日**。
   job 词表（可增补；多词 job 用 CamelCase）：`framework`（框架 / 资产）、`curriculum`（轮次内容）、
   `code`（新功能 / 新目录的编写）、`debug`（优化既有代码、查因与修复）、`research`（方案研讨）、
   `survey`（调研与对照报告）、`ProductDesign`（产品设计）、`docs`（文本修缮）、`test`（真机测试执行）。
2. **文档自指一律用 ID**，不写"本 Agent / 该 agent"。
3. **一个 ID = 一段对话 + 一个「服务对象」**：服务对象是**一个轮次**、**一个任务单元**或**一条常驻线**。
   服务对象写进名册，**它是生命周期管理的主键**。
4. **换服务对象 = 新 ID、新行，且不写 `旧 → 新` 箭头**——箭头会被读成"同一实体换了个名字"，
   而"轮次 A 的轮次线"与"轮次 B 的轮次线"是**两件不同的工作**。交接关系写成
   「**接手自** `<旧ID>`（其服务对象 = `<旧轮次>`）的未竟事项」。
5. **同一服务对象内换对话**（上下文吃紧重开）：新 ID + 备注"同一服务对象的续话，前一段 = `<旧ID>`"。
6. **新 Agent 开局**：先读名册，**自报 ID + 服务对象 + 写入范围**。

## 二、派工：三件套与派工单

### 2.1 三件套分工

| 件 | 落点 | 何时写 | 回答什么 |
|---|---|---|---|
| **派工单** | `notes/agents/dispatch/<线头>-<YYYY-MM-DD>.md` | **派之前** | 派什么活 / 边界 / 验收 |
| **名册** | `notes/agents/roster.md` | **全程** | 谁在岗 / 什么状态 / 还剩多少上下文 |
| **交接件** | `notes/handoffs/<slug>.md` | **交接时** | 做到哪 / 下一步 / 坑 |

流转：**派工单（派）→ 名册（在岗）→ 交接件（交）→ 名册（已归档）**。
三者互相**指针**，不互相复制内容（复制必然漂移）。区域说明见 `notes/agents/README.md`。

### 2.2 派工单的写法

固定七节（模板 `templates/dispatch-order.md`）：
§0 状态速览 / §1 **通用交接纪律粘块**（可直接粘贴给新 Agent）/ §2 派工表（**含「阻塞谁」列**）/
§3 **可直接粘贴的 kickoff** / §4 待拍板项 / §5 整理方自办 / §6 移交说明。

纪律：

1. **一条任务一段 kickoff**：可直接粘贴开新对话，含必读清单（带章节或行号）、交付、边界、验收——
   不要求读者再回来问。
2. **跨线任务一律进派工单**，不挂在某个项目或轮次目录下（项目目录会动，跨线读者找不到）。
3. **被派方只回填状态列**：任务状态由被派方更新，**任务定义与排序归整理方**。
4. **写清「阻塞谁」**：让"哪条任务卡住下游"一眼可见。
5. **移交**：原执行线归档后该单转**只读**；接手方要更新状态就**另开**一份派工单，不原地改写
   （保留当时的派工原貌——与"历史记录不改"同一口径）。

### 2.3 名册的维护

- 名册是**唯一**的生命状态台账；**用户拥有**，各线**只改本行**的「状态 / 最后活动 / 档位 / 归档日」，
  格式与新增行归框架线——这是"**单一写入者（按路径所有权）**"在**行**粒度上的延伸。
- **写入范围与状态分表维护**：前者很少变，后者经常变；分开后改状态不必碰长单元格。

## 三、生命周期：六态、档位、归档

1. **六态**：`待启动 → 在岗 → 交接中 → 已归档`；旁路 `阻塞`（等用户 / 等外部）、`暂停`（临时叫停）。
   台账里也常用 **`挂起（等后续任务）`** 表示旁路态：暂时不推进，但不关闭对话。
2. **上下文档位**（宽松 / 过半 / 吃紧）是**归档决策的输入**，判据沿用 `agent-context-economy.md`。
3. **归档四步**：① 判据命中（上下文吃紧 / 任务完成 / 线头转交）→ ② 交接件落 `notes/handoffs/`
   （按其 README 的固定模板）→ ③ **冷启动测试**（接手方只读「交接件 + 执行日志 + 相关 spec」能否接着干）
   → ④ 名册改「已归档」+ 归档日 + 交接件指针，用户关闭对话。
4. **轻量归档例外**：产出**全部是仓内可读文件**的线（例：文本修缮线）可**省交接件**——
   备注写清"交付物 = 仓内改动 + 执行日志条目"即可（交接件的目的是把**对话里的知识**外部化）。
5. **归档不留目录**：历史靠名册一行 + 交接件 + 执行日志表达。

## 四、与其它规则的关系

| 规则 | 关系 |
|---|---|
| `rule-sync-mechanism.md` | 规则的成熟度分级；本机制自身也按它走两级更新 |
| `agent-context-economy.md` | 给出"上下文吃紧"的可判断信号 → 归档决策的输入 |
| `git-practices.md` §7 | 派工单里命令块的写法（声明 shell、给字面量、先只读后写入） |
| 仓根入口文件（如 `CLAUDE.md`） | 启动阅读顺序里加一行：**先读名册自报 ID** |
| `templates/CLAUDE.md` 的"不主动执行指令" | 派工单 §1 的通用粘块把该纪律**再显式化一次**（新 Agent 不看入口也能守住边界） |

## 五、来源与成熟度

- **来源**：renderer-lab 2026-09-16 ~ 09-19 的实践——从"多 Agent 边界"（单一写入者 / 工作区所有权 /
  本地装置隔离）起步，经 5 条线（框架 / 轮次 / 调试 / 调研 / 文本修缮）实际运行后收敛为
  **身份 + 派工 + 生命周期**三段；期间踩到的具体坑（`旧 → 新` 写法歧义、跨线任务挂错位置、
  归档无判据、任务范围不明确、派工单原地改写）都已并入上文各条。
- **成熟度**：第一处实践已验证（5 条线 / 2 次归档 / 1 次移交）。第二处复现后视为稳定规则；
  各仓库可按自己的目录习惯改落点，但**三件套分工与"服务对象"语义**建议保持。
