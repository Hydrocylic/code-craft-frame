## 0. 目的与适用

**问题**：很多时候环境本身就不满足条件——上来就跑长测，跑完才发现数据不可用，浪费一整轮。
**做法**：把“能不能测”从“测量”里**独立出来**，做成**递进的四层自检**，逐层通过才进入测量。

适用：性能测量、真机采集、无头渲染诊断、任何“产物是数据/图像”的轮次。
不适用：纯阅读/纯文档轮次。

## 1. 四层自检

| 层 | 检查什么 | 一次实例（回推） |
|---|---|---|
| **平台层** | GPU 非软件后端 / 能否设目标视口 / DPR / 上下文属性 | headless 落 SwiftShader（脚本拒绝并退出 1）；设备工具栏停在“Fit 态”→ 实际视口 1520×835 |
| **应用层** | 目标场景**已应用** / 参数口径正确 / 规模下限 | 默认场景（约 1134 三角形）让“弱判据”假性放行（与 `?scene=` 异步束存在竞态） |
| **产物层** | 图像尺寸 = 视口 / 位深 / 非隔行 / 跨图可比 | dpr=2 手工截图产出 2560×1440（2× 上采样，PSNR 被抬高 3–6 dB）；落盘后用 IHDR 校验 |
| **过程层** | 采集期间不被节流 / 无 context loss / 前后吞吐一致 | 后台标签 rAF 被节流直接失真；**截图本身拖慢主线程**（四张图间隔比理论慢近一倍） |

判定口径：每层给**可打印的判据**（不是“看起来对”）——例：`innerWidth = canvas = W×H`；
`activeScene = <目标场景>` 且 `uTriCount ≥ <下限>`；PNG 的 IHDR 尺寸 = 目标视口。

## 2. 三条硬要求

1. **fail-fast 且不产出数据**：任一层不过 → **中止并保留原始输出**（日志/错误码），
   宁可白跑一轮，也不产出污染数据（污染数据比没数据更贵——它会进结论）。
2. **自检与测量分开、可独立跑（2026-09-22 起：由“可做”升为“必做”）**：采集脚本**必须**提供 `--preflight` 之类模式，
   让“环境不行”在 **30 秒内**暴露，而不是在长测末尾才暴露。至少给出**三件前置判据**：
   ① **目标可见性**（目标标签是可见的活动标签——多标签下“取第一个 page target”会造成 `S=0` 静默空转）；
   ② **是否被节流**（后台标签 rAF 被降频）；③ **目标选择**（场景/参数/视口已按口径生效）。
   **失败形态提示**：前置条件不满足时的典型表现是**“静默等待”而不是报错**（一次 1520×835 白采一轮；
   另一次 `S=0` 持续 101 s、若不人工中止就是 20 min 白烧）——preflight 要消灭的正是这个形态。
3. **人工步骤必须有自检收尾动作**：每个“人工操作”（设视口、切场景、开前台）后面跟一条**可粘贴的确认片段**——
   否则“操作没生效”会被误读成“设备不支持”（一次 1520×835 正是此例）。

## 3. 与既有机制的关系

| 机制 | 关系 |
|---|---|
| 任务工作流 §验证门槛 | 门槛管“**数据够不够好**”，本 spec 管“**环境能不能测**”——两者是递进关系，先过本 spec 再谈门槛 |
| 任务工作流 §采集协议 | 采集协议里的“取样序列/裁切约定”决定**怎么测**；本 spec 决定**能不能开始测** |
| `headless-reproduction.md` | 无头场景的**失败后**分层排查（编译/链接/校验/运行）；本 spec 是**失败前**的前置自检，二者互指 |
| `templates/conventions-card.md` | 自检产出的“平台/应用/产物”判据应收进口径卡，供后续轮次复用 |

## 4. 落地形态（**必做**，2026-09-22 起）

- 采集脚本带 `--preflight`：只跑四层检查、打印表格（层 / 判据 / 实测 / 通过否），**不写任何数据文件**；
- 记录表模板里留一节“自检结果”（层 × 判据 × 实测），与数据同存——复盘时能判断“这组数据的可信度”；
- **人工步骤也要有收尾判据**：凡“人来操作的步骤”（设视口、开前台、发布、上传），块内必须带一条**可粘贴的确认动作**
  （例：发布后 `Ctrl+U` 看首页引用是 `./assets/…` 还是 `/src/main.js`）——见 `platform-pitfalls.md` 与
  `templates/manual-task-sheet.md`。

## 5. 来源与成熟度

- **来源**：一次性能基线实践（2026-09-17 ~ 09-18）；用户提出“递进式测试方法”，实例任务落成四层，随后提升为 spec（2026-09-18）。
- **成熟度**：**首次实践**（第一级）。第二处复现（另一任务或另一项目）出现同一四层 → 作为第二级候选提上游。
