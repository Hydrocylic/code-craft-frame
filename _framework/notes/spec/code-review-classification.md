# 代码品读分类与路由规范

> 区域: spec（规范区）
> 框架版本: v3.0
> 创建: 2026-08-10
> 来源: 实例代码品读实践反馈

---

## 适用范围

仅在任务确有独立代码品读交付时使用本分类。普通实现自查、缺陷修复或简短复盘可直接写在任务交付件，不要求建立 `code-review.md`，也不因项目类型自动强制 T1–T7 分类。

选择独立品读件时，可用下文分类整理发现；只记录实际出现的类别，未出现的类别不建空段。

---

## 一、设计理念

代码品读不是“检查代码有没有 bug”，而是**对产出代码的结构性复盘**：

- 这段代码实际做了什么？
- 用了什么模式？为什么选这个模式？
- 有哪些可以改进的地方？
- 通过这段代码发现了哪些自己不懂的东西？

品读中发现的每一项内容都标注类型标记（T1–T7），不同类型有不同的处理方式和最终归宿。**分类的目的是让每一条发现都有明确的去处，不堆积在品读文件中腐烂。**

---

## 二、T1–T7 分类路由表

| 标记 | 含义 | 在品读中的处理 | 最终归宿 |
|------|------|---------------|----------|
| **T1** | 有直接答案的语法/文档问题 | **在品读中写答案**（标题 + `📝 [日期]` 时间戳） | 积累后 Agent 按区域批量转移 → 知识库或长期读物（如有） |
| **T2/T7** | 结构分析 + 设计取舍（允许模糊，不强行区分） | 留在品读（核心产出），叙事性分析 | 重要决策抄送决策记录（如有） |
| **T3** | 性能优化想法 | 记录三元组：潜在需求 + 可能方法 + 可能效果 | → 问题清单的候选区（暂不建新文件，积累后再议） |
| **T4** | 大规模技术背景路标（难以短期深入） | 品读简要标记 | → 知识库“待深入”条目（如有） |
| **T5** | 可执行改进项（明确的 TODO） | 品读 checkbox 列表 | 属于当前任务的进 plan；跨任务的入问题清单 |
| **T6** | 验证待办（需实证测试的假设） | 品读简要记录 | → 问题清单（集中评估价值后再决定是否排期） |

### 各类型的详细说明

#### T1 — 有直接答案的语法/文档问题

“这段代码用了 `async/await`，我不太确定 `Task.Run` 和直接 `await` 的区别是什么？”

- 这类问题有**明确的、可以通过查资料得到答案**
- 在品读中直接写答案，不推迟到后续
- 标注 `📝 [日期]` 时间戳
- 后续 Agent 按时间戳批量迁移到知识库或长期读物（若该类读物存在）

#### T2/T7 — 结构分析与设计取舍

“这里选择了观察者模式而不是事件总线，因为模块间耦合度低、不需要广播——但代价是每个观察者都要显式注册。”

- 这是品读的**核心产出**
- 叙事性分析：为什么这样设计？有什么取舍？
- 允许 T2（结构分析）和 T7（设计取舍）不强行区分——它们往往是同一话题的两面
- 重要决策抄送决策记录（如有）

#### T3 — 性能优化想法

“当前每帧都重新分配数组，如果对象池化可以减少 GC 压力——但实际帧率还没测量，不确定是否构成瓶颈。”

- 记录三元组：**潜在需求** + **可能方法** + **可能效果**
- 不立即实施——先进入问题清单的候选区积累
- 等有足够上下文或实际性能数据后再评估

#### T4 — 大规模技术背景路标

“这里涉及的 Job System 和编译优化是一个大主题，不是当前任务能覆盖的。”

- 识别出“这里有一个很大的知识领域”
- 品读中简要标记，不展开
- 进入知识库作为“待深入”条目（如有）

#### T5 — 可执行改进项

- [ ] 提取重复的配置解析逻辑到独立类
- [ ] 为输入数据结构添加单元测试

- 明确的、可执行的 TODO
- 属于当前任务范围内 → 直接在 plan/log 中跟进
- 跨任务的 → 进入问题清单
- 被排期的 → 创建新任务计划

#### T6 — 验证待办

“假设帧率瓶颈在图像拷贝而非推理——需要写 benchmark 验证。”

- 需要**实证测试**的假设
- 先进入问题清单集中评估
- 验证价值高的 → 排入任务计划
- 验证价值低的 → 保留在问题清单作为记录

---

## 三、T1 迁移流程（由 Agent 按需触发）

1. 定位品读文件中 `## N、T1 ·` 开头的区域
2. 按 `📝 [日期]` 时间戳判断条目新旧
3. 将问答条目提炼为知识库/长期读物的标准格式（问题 + 答案 + 日期 + 来源）
4. 在品读原位置替换为简短引用：`> → 已迁移到 <读物> QXX`
5. 用户可指定时间范围（如“迁移某月之前的全部 T1”）

---

## 四、核心原则

1. **减少跳转，增加信息密度** — T1 先在品读中写完整答案，不提前做引用跳转。读者不需要在品读和知识库之间反复横跳。
2. **时间戳驱动迁移** — 时间戳是 Agent 定位区域、判断新旧、决定删留的唯一锚点。
3. **粗糙记录优先** — T2/T7 不强行区分；T3 先不建新文件。
4. **问题集中评估** — T6 不进任务目录，先进问题清单，避免验证任务分散遗失。
5. **分类即归宿** — 每条发现标注类型的那一刻，就确定了它的最终去处和执行节奏。
